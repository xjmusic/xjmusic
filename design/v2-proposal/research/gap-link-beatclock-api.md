# Gap map: Ableton Link API semantics, rusty_link coverage, cpal clocks and the MIDI-clock fallback for `BeatClock`

Scope: what `07-session-protocol.md` ("Clock", "Mapping chain time to beats") and `03-architecture.md` ("Time model", lines 104-116) need from Ableton Link, the `abl_link` C API, `rusty_link` 0.4.9, `cpal` 0.18.2 and MIDI 1.0 real-time messages. This complements `external-stack-research.md` section 4 (release history, license, pin) and `engine-api-lifecycle.md` (chain micros inside the engine). Everything below was read from source; line numbers refer to the files named. Sources were downloaded to `scratchpad/understand/link-src/` (Link master = 4.1.1 and the commit `0fc58dc` that the rusty_link GitHub submodule points at), `scratchpad/understand/rusty-link-crate/rusty_link-0.4.9/` (the crates.io tarball, which vendors its own copy of Link) and `scratchpad/understand/cpal-crate/cpal-0.18.2/`.

Repository facts first: `grep -rIli midi engine/ workstation/` returns **0 files**; nothing in the repo mentions Ableton, `abl_link` or `rusty_link`. The only host clock in the C++ example is `SDL_GetTicks()` milliseconds (`engine/example/XJPlayer.cpp:62,79`, stored in a `Uint32 AtChainMicros`), and the engine itself never reads a clock for chain time; it receives `atChainMicros` from the host (`engine-api-lifecycle.md` section 4). Link, cpal timestamps and MIDI clock are therefore greenfield for `xj-transport`.

## 2. SessionState capture/commit: audio thread versus app thread

`Link.hpp:62-71` (identical text in `abl_link.h:51-60`): "Link provides one session state capture/commit method pair for use in the audio thread and one for all other application contexts. In general, modifying the session state should be done in the audio thread for the most accurate timing results. The ability to modify the session state from application threads should only be used in cases where an application's audio thread is not actively running or if it doesn't generate audio at all. Modifying the Link session state from both the audio thread and an application thread concurrently is not advised".

| Method | Link.hpp | Thread-safe | Realtime-safe | Implementation |
|---|---|---|---|---|
| `captureAudioSessionState()` | 183 | **no** | yes | `Link.ipp:142-146` → `Controller::clientStateRtSafe()` (`Controller.hpp:231-265`): never blocks; returns a per-controller cache `mRtClientState`, refreshed from a triple buffer (`mClientState.getRt()`) only when no local rt commits are pending and the 1 s `kLocalModGracePeriod` (`Controller.hpp:82`) has elapsed since the last rt commit |
| `commitAudioSessionState(s)` | 195 | **no** | yes | `Link.ipp:149-154` → `setClientStateRtSafe` (`Controller.hpp:268-304`): clamps tempo, pushes the diff into a lock-free `RtClientStateSetter` (`Controller.hpp:552-628`) drained on a Link thread, with a 500 ms fallback timer (`kRtHandlerFallbackPeriod`, line 83); the commit timestamp is `clock().micros()` at the call |
| `captureAppSessionState()` | 209 | yes | **no** | `Link.ipp:157-161` → `mClientState.get()` (`Controller.hpp:203`), mutex-guarded |
| `commitAppSessionState(s)` | 220 | yes | **no** | `Link.ipp:164-169` → `setClientState` (`Controller.hpp:207-225`) applies under lock, then `handleClientState` (424-470) updates the session timeline and broadcasts |

Shared mechanics:
- A `SessionState` holds `mOriginalState` and `mState` (`Link.hpp:378-379`). On commit, `toIncomingClientState` (`Link.ipp:39-54`) sends only the fields that changed; `setClientStateRtSafe` returns immediately if nothing changed (`Controller.hpp:270-273`). Committing an unmodified capture every callback is therefore cheap but pointless.
- `mbRespectQuantum = numPeers() > 0` is frozen at capture (`Link.ipp:145,160`); it decides whether `requestBeatAtTime` quantizes (section 3).
- "Thread-safe: no" on the audio pair means one thread only: whichever thread owns the cpal output callback must be the only caller of `capture_audio_*`/`commit_audio_*`. The app pair may be called from any number of control/UI threads. The two pairs may both *read* concurrently (the LinkHut examples do: `AudioEngine.ipp:199` on the audio thread, `abl_link_example_main.c:150` on the UI thread); only concurrent *writes* from both are discouraged.
- Callbacks (`setNumPeersCallback`, `setTempoCallback`, `setStartStopCallback`, `Link.hpp:134,146,159`) run "on a Link-managed thread" and hold `mCallbackMutex` while running (`Link.ipp:62-76`); registering a callback from inside a callback would deadlock on that `std::mutex` (`Link.ipp:113-133`). Tempo callback fires only when the session tempo changes (`Controller.hpp:377-380`).
- After a local rt commit, the audio thread does not see competing network changes for up to 1 s (`Controller.hpp:237-260`); a station that nudges tempo from the audio thread is briefly deaf to a peer doing the same.

`abl_link` adds one wrinkle: `abl_link_session_state` is heap-allocated (`abl_link.cpp:152-156`, `new ableton::Link::SessionState`), and capture is a struct assignment into it (`abl_link.cpp:163-168, 177-182`). rusty_link's doc on `capture_audio_session_state` accordingly says "The session_state should not be created on the audio thread" (`src/abl_link.rs:91-93`); create one `SessionState` up front and move it into the callback closure (`SessionState` is `Send` but not `Sync`, `src/session_state.rs:22`).

**Documentation bug in rusty_link 0.4.9:** `capture_app_session_state` is documented "Thread-safe: no / Realtime-safe: yes" (`src/abl_link.rs:98-104`), the reverse of the C header it claims to copy (`abl_link.h:212-213`: thread-safe yes, realtime-safe no). The C header is right; the Rust doc comment is wrong.

## 3. Exact meaning and units of the SessionState API

All times are `std::chrono::microseconds` on Link's own clock (section 4); in C and Rust they are `int64_t`/`i64` micros on that same clock (`abl_link.h:148,246-348`; `session_state.rs:64-170`). Beats and quantum are `double` beats. Internally beats are `int64` **micro-beats** (`Beats.hpp:35-37`: `llround(beats * 1e6)`), and tempo travels on the wire as integer **micros per beat** (`Tempo.hpp:47-49`, `microsPerBeat() = llround(60e6 / bpm)`), which is why `Controller.hpp:341-342` notes "999 bpm is transferred as 60606 us/beat and received as 999.000999...". The valid tempo range is **20..999 bpm**, clamped on every commit and every received timeline (`ClientSessionTimelines.hpp:31-38`, `Controller.hpp:277,343`).

The timeline is one affine map `Timeline{tempo, beatOrigin, timeOrigin}` with `toBeats(t) = beatOrigin + (t - timeOrigin)/microsPerBeat` (`Timeline.hpp:44-52`). It "starts running from beat 0 at the initial tempo when constructed" and "always advances ... even if transport is stopped" (`Link.hpp:42-44`).

| Call | Meaning (source) | Notes for the spec |
|---|---|---|
| `tempo()` | bpm of the timeline; "a stable value that is appropriate for display ... Beat time progress will not necessarily match this tempo exactly because of clock drift compensation" (`Link.hpp:251-257`) | Do not derive beat positions by integrating `tempo()`; always ask `beatAtTime` |
| `setTempo(bpm, atTime)` | `Link.ipp:202-209`: builds a new clamped timeline whose beat at `atTime` equals the old beat at `atTime`, then recomputes `timeOrigin` so `beatOrigin` is preserved. The whole affine map changes, so beats *before* `atTime` are re-mapped too | Only valid for future scheduling; never re-evaluate past instants after a tempo change |
| `beatAtTime(time, quantum)` | `Link.ipp:212-217` → `toPhaseEncodedBeats` (`Phase.hpp:76-82`): the raw `tl.toBeats(time)` snapped to the value nearest it whose phase relative to `quantum` matches the session grid; "The result will deviate by up to +- (quantum/2) beats compared to the result of tl.toBeats(time)". "The magnitude of the resulting beat value is unique to this Link instance, but its phase with respect to the provided quantum is shared among all session peers" (`Link.hpp:267-271`) | **Magnitude is local, phase is shared.** `fmod(beatAtTime(t,q), q) == phaseAtTime(t,q)` for non-negative beats |
| `phaseAtTime(time, quantum)` | `[0, quantum)`, handles negative beats correctly, returns 0 when quantum is 0 (`Link.hpp:275-285`, `Phase.hpp:34-49`) | With `quantum = barBeats` this is the beat-within-bar; the downbeat is the instant phase wraps to 0 |

| `setIsPlaying(isPlaying, time)` / `isPlaying()` / `timeForIsPlaying()` | user intent to start/stop transport at `time` (`Link.ipp:280-296`); shared only when `enableStartStopSync(true)`; "The start/stop state can only be changed by the user ... persists when joining or leaving a Link session" (`Link.hpp:233-241`) | Transport stop does not stop the beat timeline. | `requestBeatAtStartPlayingTime(beat, quantum)` | no-op unless playing; else `requestBeatAtTime(beat, timeForIsPlaying(), quantum)` (`Link.ipp:299-306`) | LinkHut uses `(0, quantum)` on every start so beat 0 lands on the shared start instant (`AudioEngine.ipp:216-221`) |

| `clock()` | the platform clock object; only `micros()` is portable (`Link.hpp:161-170`); darwin/windows also offer `ticksToMicros`/`microsToTicks` (`darwin/Clock.hpp:46-56`, `windows/Clock.hpp:44-52`) | The C API exposes only `abl_link_clock_micros` (section 5) |

Join semantics that follow from the implementation: when a peer timeline arrives, a session adopts it only if its `beatOrigin` is larger ("We use beat origin magnitude to prioritize sessions", `Sessions.hpp:223-241`); a client's own edits bump the session `beatOrigin` to at least `curSession.beatOrigin + 1 µbeat` so they win (`ClientSessionTimelines.hpp:86-99`). On join, `updateClientTimelineFromSession` (`ClientSessionTimelines.hpp:45-63`) keeps the client's **beat magnitude** at the current instant (`curClient.toBeats(atTime)`) and sets the client's `timeOrigin` to the host time of **session beat 0**, "the origin of the quantization grid for all participants". Phase is then forced onto that grid, so the joiner's `beatAtTime` jumps by up to ±quantum/2; TEST-PLAN.md:64-67 says exactly this ("an app should adjust to the existing session's tempo and phase, which will usually result in a beat time jump. Apps that are already in a session should never have any kind of beat time or audio discontinuity").

Session clock alignment between machines is Link-internal: each peer measures a `GhostXForm{slope, intercept}` (`GhostXForm.hpp:32-58`) to a shared "ghost" time by ping/pong, 5 measurement rounds on a 50 ms timer collecting more than 100 data points (`Measurement.hpp:45-46,110-130,185-200`). Neither the ghost time nor the xform is reachable through `Link.hpp` or `abl_link.h`. **Two machines therefore share only phase, tempo and (optionally) the start/stop instant; they share neither beat magnitude nor host time.**

## 4. What `clock().micros()` is on each OS, and how it relates to cpal and chain micros

Platform selection is `platforms/Config.hpp:61-100` by `LINK_PLATFORM_WINDOWS|MACOSX|LINUX` (rusty_link's CMake sets these through Link's own `AbletonLinkConfig.cmake`).

| OS | Link clock (file:lines) | cpal 0.18.2 `StreamInstant` source (`src/timestamp.rs:19-29`, host code) | Same origin? |
|---|---|---|---|
| macOS | `mach_absolute_time()` ticks × `numer/(denom·1000.)` as `double`, `llround` → µs (`darwin/Clock.hpp:38-60`) | `mach_absolute_time()`; `host_time_to_stream_instant(mHostTime) = mHostTime·numer/denom` ns in `u128` (`coreaudio/mod.rs:69-77`); `callback` = the driver's `AudioTimeStamp.mHostTime` (`macos/device.rs:906`), `playback = callback + frames_to_duration(device buffer frames + kAudioDevicePropertyLatency + kAudioDevicePropertySafetyOffset)` (`macos/device.rs:913-921, 1043-1050`) | **Yes** (both since boot). `link_micros ≈ instant.as_nanos()/1000` within ±1 µs of rounding |
| Windows | `QueryPerformanceCounter` × `1e6/QueryPerformanceFrequency` as `double`, `llround` (`windows/Clock.hpp:37-61`) | `QueryPerformanceCounter` → 100 ns units → `StreamInstant` (`wasapi/stream.rs:505-520`); `playback = callback + buffered + stream_latency` where `stream_latency` is `IAudioClient::GetStreamLatency` (`wasapi/stream.rs:967-983`, `wasapi/device.rs:914-919`) and `buffered` is frames written minus `IAudioClock::GetPosition` (`stream.rs:920-930`) | **Yes** (QPC since boot). ASIO is different: cpal's ASIO instants come from `timeGetTime()` (`timestamp.rs:23`), a millisecond clock, unrelated to QPC; use the HostTimeFilter path there |
| Linux | `clock_gettime(CLOCK_MONOTONIC_RAW)`, ns/1000 integer division (`linux/Clock.hpp:38-52`; `Config.hpp:83` picks `ClockMonotonicRaw`; FreeBSD maps RAW to MONOTONIC, lines 31-33) | ALSA: `snd_pcm_status_get_htstamp()` with `tstamp_type` set to `MonotonicRaw`, falling back to `Monotonic` (`alsa/mod.rs:1682-1690`), **expressed as elapsed time since stream creation** (`alsa/mod.rs:695-707, 736-740, 780-816`; three modes `CreationInstant` = `Instant::now()` delta, `SystemClock`, `AudioLink`). JACK: `jack_get_time()`/`cycle_times().current_usecs` (`jack/stream.rs:393-407, 507`), JACK's own clock. PipeWire: `pw_stream_get_time_n()` (`timestamp.rs:27`). PulseAudio: `std::time::Instant` (`timestamp.rs:28`) | **No.** ALSA instants start at 0 at stream creation and may be on `CLOCK_MONOTONIC` (NTP-slewed) while Link is on `MONOTONIC_RAW`; JACK and PipeWire are different clocks again |

`timestamp.rs:12-15` states the rule: "Across different streams, origins are not guaranteed to be shared. On some hosts each stream starts its own independent clock at zero". So a portable `xj-transport` must never equate `StreamInstant` with Link micros; it must maintain a per-stream affine map `StreamInstant → Link µs`, either by linear regression (Link's `HostTimeFilter`, 512 points, `HostTimeFilter.hpp:33-83`; rusty_link's port, `host_time_filter.rs:36-58`) over `(sample position, link.clock_micros() sampled inside the callback)`, or, on macOS/Windows, by direct conversion with a one-time sanity check that `|clock_micros() - callback.as_nanos()/1000|` is a few milliseconds at most.

Latency: what Link wants in `beatAtTime` is the host time at which the **first sample of the buffer leaves the DAC**. The LinkHut platforms compute `bufferBeginAtOutput = hostTime + mOutputLatency` (`AudioPlatform_CoreAudio.ipp:53-57`, `Wasapi.ipp:287-294`, `Asio.ipp:102-111`, `Jack.ipp:80`), where `hostTime` is either the driver's buffer timestamp (CoreAudio `inTimeStamp->mHostTime` via `ticksToMicros`) or `HostTimeFilter::sampleTimeToHostTime(samplePosition)` (WASAPI, ASIO), and `mOutputLatency` is `kAudioDevicePropertyLatency / sampleRate` on CoreAudio (`CoreAudio.ipp:218-238`, with the comment "the buffer, stream and safety-offset latencies are part of inTimeStamp->mHostTime"), `GetStreamLatency` on WASAPI (`Wasapi.ipp:238-242`), `ASIOGetLatencies` output latency plus one buffer on ASIO (`Asio.ipp:213-227`), `jack_port_get_latency_range(JackPlaybackLatency).max` on JACK (`Jack.ipp:55-67`). cpal's `OutputStreamTimestamp.playback` ("The predicted instant that data written will be delivered to the device for playback", `timestamp.rs:56-62`) is the same quantity by intent, and the rusty_link LinkHut port uses `playback.duration_since(callback)` as its output latency (`examples/link_hut/audio_platform_cpal.rs:120-125`) added to the filtered host time (`audio_engine.rs:42-46`). Note the CoreAudio discrepancy: Link adds only `kAudioDevicePropertyLatency` to `mHostTime`, while cpal adds device buffer frames **and** latency **and** safety offset (`macos/device.rs:913-921`). One of the two over- or under-compensates by roughly a buffer; only the TEST-PLAN AUDIOENGINE-1 loopback measurement (section 6) can say which, per device.

Chain micros: `03-architecture.md:116` defines V2 chain time as "an affine function of device frames, re-estimated continuously". With Link, the clean chain is: device frame → (`HostTimeFilter`) → Link µs → (`beatAtTime`) → beat; and back via `timeAtBeat`. The engine side rounds differently from Link: `Fabricator.cpp:752-755` computes segment micros as `long(MICROS_PER_MINUTE / tempo * beats)` and `CraftWork.cpp:415-429` sums `begin = last.begin + last.duration`, while Link quantizes tempo to integer µs/beat (`Tempo.hpp:47-49`) and beats to µbeats. At 124 bpm Link's beat is 483,871 µs (effective 123.99991 bpm) against the engine's 483,870.97 µs; a 16-beat segment differs by 1 µs and an hour of segments by roughly 240 µs. Inaudible, but the session test "assert identical foundations per segment span" (`07-session-protocol.md`, Testing) must compare beats, not micros, and `xj-transport` should derive each segment's chain begin from `timeAtBeat(beginBeat)` rather than from summed segment durations so the two clocks cannot drift apart over a show.

Missing from `abl_link`, and therefore from rusty_link:
- `BasicLink<Clock>` with a custom clock (`Link.hpp:78-79`): the C API always uses the platform clock. No `stl::Clock` (`steady_clock`) option.
- `Clock::ticksToMicros`/`microsToTicks`: a CoreAudio `mHostTime` cannot be converted with Link's own factor; use `mach_timebase_info` yourself (cpal already does, `coreaudio/mod.rs:69-77`) or regress.
- `SessionState::operator==` and any access to `ApiState`/`Timeline` internals (`Link.hpp:373-381`); the session id, ghost transform and measurement state are unreachable.
- Link Audio: bound by bindgen but private (`lib.rs:11-16`; `CHANGELOG.md:5`).
- Any way to receive callbacks without `'static + Send` closures; the callbacks run on Link's thread, so the Rust side must bridge them into the station's control loop (channel or atomics).

Differences in the Rust `HostTimeFilter` port versus `HostTimeFilter.hpp`: the caller supplies `clock_micros` (the C++ samples the clock internally, `HostTimeFilter.hpp:56`); `reset()` reallocates the point buffer (`host_time_filter.rs:30`, `Vec::with_capacity`), so it is **not** realtime-safe and should be called only outside the callback; `sample_time_to_host_time` asserts `clock_micros >= 0` (line 37) and `linear_regression` asserts a non-empty buffer (65), both panics that would unwind the audio callback; sums are `u128` (63-89) so absolute frame counts over long shows are safe. Both ports use 512 points and recompute the full regression per call (512 multiply-adds per callback).

Build facts (`Cargo.toml`, `build.rs`): edition 2024; `cmake` 0.17.3 and `bindgen ^0.72.1` as build dependencies (libclang required at build time); static library `lib_abl_link` (`build.rs:20`); links `c++` on macOS and `stdc++` on Linux (`build.rs:11-16`); on Windows MSVC is assumed by Link's own CMake. Cross-compiling Linux→Windows was fixed in 0.4.8 (`CHANGELOG.md:9`). License `GPL-2.0-or-later` (`Cargo.toml:30`); the README states rusty_link "has to be under the GPLv2+ as well" (`README.md:88-92`), so Ableton's proprietary grant must cover a fork or re-licensed binding, as the external-stack map already notes.

## 7. Quantum, bars, the epoch, and whether B₀ can be a session constant

**Quantum ↔ barBeats.** `phaseAtTime(t, barBeats)` is the beat-within-bar on the shared grid, and the downbeat is where it wraps to 0; `floor(phaseAtTime(t, quantum)) == 0` is how LinkHut picks the accented click (`AudioEngine.ipp:176-182`). All quanta share the same grid origin (session beat 0, `ClientSessionTimelines.hpp:53-56`), so an XJ station with `barBeats = 3` and an MPC in 4/4 agree on beats and coincide on downbeats every 12 beats. Since `barBeats` is per program and can change at a macro boundary (`11-resolutions.md` Q14), the quantum the station passes to Link changes with it; the grid does not move, only the station's notion of "bar" does. Segment lengths are whole bars (`totalBeats` is `mainSequence->total`), so a segment begin that lands on phase 0 keeps every later segment on phase 0 while `barBeats` is constant.

**B₀ cannot be a session constant in Link beat units.** Beat magnitude is per instance (`Link.hpp:267-269`; `abl_link.h:251-253`); two stations reading `beatAtTime` for the same wall instant get values that agree only modulo quantum, and a joining station's value jumps (`TEST-PLAN.md:64-67`). Nor can the conductor's chain time T₀ be shared directly: Link's clock is per machine (section 4) and the inter-machine ghost transform is private. Three workable ways to pin the epoch, all compatible with the `welcome` message in `07-session-protocol.md`:

1. **Anchor on the Link start instant.** With start/stop sync enabled, `timeForIsPlaying()` is the same instant on every peer (mapped through the ghost transform, `Controller.hpp:94-103`). If every XJ station calls `request_beat_at_start_playing_time(0.0, barBeats)` when it observes `is_playing()` turn true, as LinkHut does (`AudioEngine.ipp:216-221`), then beat 0 is the first grid downbeat at or after that instant for all of them and magnitudes agree. The magnitude-only re-anchor is local and not broadcast (section 3). Cost: depends on start/stop sync being on, and any Link peer (an MPC) pressing Stop/Play re-anchors the room.
2. **Bar identity over the XJ protocol, phase from Link.** The conductor's `welcome` and every `foundation` record carry the bar number (or `beginBeat` in conductor units) plus the conductor's Link-clock micros at that downbeat; the follower uses the NTP-style offset estimate that the `session` clock needs anyway to translate the conductor's micros into its own Link clock to within tens of milliseconds, then snaps to the nearest grid downbeat with `timeAtBeat`. Bars are about 2 s at 124 bpm, so a 100 ms offset error cannot pick the wrong bar. No dependence on start/stop sync; no re-anchoring of Link state at all. Each station then keeps a private affine `bar ↔ local Link beat` map.
3. **`force_beat_at_time` by the conductor** to make its magnitude the session's: rejected; forcing shifts `timeOrigin` for everyone (`Link.ipp:250-262`) and `Link.hpp:325-346` reserves it for bridging an external clock, which is exactly the `session`→Link bridge, not the normal path.

Option 2 is the one that keeps Link read-only on followers and matches "Followers treat the beat as truth and compute their own chain time from it". The `welcome` epoch then reads: `(conductorBar, conductorLinkMicrosAtThatDownbeat, barBeats)`, and the follower derives `(T₀_follower, B₀_follower)` locally.

**The `session` clock and MIDI clock out.** When Link is absent, the conductor's `BeatClock` is the truth and followers estimate offset by round trips (`07-session-protocol.md`, Clock). For external gear the station emits MIDI 1.0 System Real-Time messages ([midi.org summary](https://midi.org/summary-of-midi-1-0-messages)):

| Byte | Message | Rule |
|---|---|---|
| `F8` | Timing Clock | "Sent 24 times per quarter note", i.e. at `timeAtBeat(k/24)` for every integer k; period `2,500,000 / bpm` µs (20,161 µs at 124 bpm; 125,000 µs at 20 bpm; 2,503 µs at 999 bpm) |
| `FA` | Start | "Start the current sequence playing"; receivers begin on the first `F8` after it, so send `FA` just before the downbeat's `F8` |
| `FB` | Continue | resume from the position last sent with `F2` |
| `FC` | Stop | stop; receivers ignore `F8` while stopped but the station should keep sending `F8` so tempo-tracking gear stays locked |
| `F2 ll mm` | Song Position Pointer | 14-bit count of "MIDI beats (1 beat = six MIDI clocks)" = sixteenth notes since song start, `ll` is the low 7 bits, `mm` the high 7 bits (`value = ll | (mm << 7)`); only meaningful while stopped, before `FB`. Maximum 16,383 sixteenths = 4,095.75 quarter notes, about **33 minutes at 124 bpm**, so a multi-hour show must either never re-sync via SPP after start or send `FC`, `F2 (pos mod 16384)`, `FB` at a bar boundary |
| `FE` | Active Sensing | optional, every ≤300 ms; not needed for clock |

`midir` (already in the stack per `external-stack-research.md` §3) sends immediately; `MidiOutputConnection::send(&[u8])` has no timestamp parameter, so the `F8` train needs a dedicated high-priority thread that sleeps until `timeAtBeat(k/24)` on the `BeatClock` and sends; typical receivers smooth clock jitter but ±1 ms is the bar to aim for. In Link mode the same emitter can run off `beatAtTime`, which gives Link-less gear a path into a Link room (the proposal's "MIDI clock out as fallback for gear", `11-resolutions.md:108`).

## 9. Implications for V2 specs

1. **Name the Link version by what the crate compiles, not by the submodule pointer.** rusty_link 0.4.9 on crates.io vendors Link 4.0.0b3 (C++17, LinkAudio present); `abl_link_create` returns a `LinkAudio`. The `xj-transport` spec should pin Link 4.1.1 in a fork of the binding (or vendor `abl_link.cpp` + Link headers directly behind `bindgen`) and verify by packet capture that a LinkAudio instance with audio disabled is wire-compatible with Link 3 peers (MPCs).
2. **One writer.** Reads may happen on both the cpal callback (audio pair) and the control thread (app pair), but all *commits* should come from exactly one side. Ableton's recommendation and the 1 s local-modification grace period (`Controller.hpp:82,237-260`) favour committing from the audio thread via a lock-free command queue (LinkHut's `EngineDataSignals` atomics, `AudioEngine.hpp:63-69`); if the spec commits from the control thread instead, it must document that `set_tempo(bpm, at)` lands at control-thread "now" rather than at a buffer boundary.
3. **`SessionState` is a heap object.** Allocate it once outside the callback, move it into the closure (`Send`, not `Sync`), and never create or drop one in the audio thread (`abl_link.rs:91-93`, `session_state.rs:22-28`). The rusty_link doc comment on `capture_app_session_state` has its safety flags reversed; cite the C header.
4. **Beat magnitude is per station; only phase, tempo and the transport instant are shared.** The epoch in `welcome` must not be "(T₀, B₀) in Link beats". Specify option 2 of §7 (bar identity plus conductor Link-micros over the XJ connection, phase from Link) or option 1 (anchor beat 0 on the shared transport-start instant, which requires start/stop sync on). Never `force_beat_at_time` in Link mode except in the dedicated `session`→Link bridge.
5. **Quantum is `barBeats` and changes with the main program.** The grid does not move when `barBeats` changes; downbeats of a 3-beat station and a 4-beat MPC coincide every 12 beats. The DSP must schedule from `time_at_beat`, never from frozen beat→frame tables, because a follower's own `beat_at` jumps by up to ±quantum/2 when it joins (TEST-PLAN BEATTIME-2 note).
6. **Clocks differ per OS.** Link: `mach_absolute_time`, QPC, `CLOCK_MONOTONIC_RAW`. cpal `StreamInstant`: same base as Link on macOS and WASAPI; a stream-relative, possibly `CLOCK_MONOTONIC` value on ALSA; JACK's and PipeWire's own clocks on Linux; `timeGetTime()` on ASIO. The transport spec must own a per-stream `StreamInstant → Link µs` map (regression, 512 points, as both `HostTimeFilter` ports) and treat direct equality as a macOS/WASAPI fast path with a start-up sanity check, never as the design.
7. **Evaluate `beat_at` at DAC time.** `callback + output latency`; cpal's `playback` is the intended source, but cpal's CoreAudio `playback` adds buffer + latency + safety offset while Link's own example adds only `kAudioDevicePropertyLatency` to `mHostTime`. Make AUDIOENGINE-1 (<3 ms against LinkHut, `TEST-PLAN.md:90-99`) a Phase 0 exit criterion per host, with a per-device latency trim setting, and remember the engine already pre-shifts picks by `transientSeconds`.
8. **Tempo ownership rules from TEST-PLAN TEMPO-2/3/5.** Construct `AblLink::new(current_bpm)`; never push a template's program tempo into Link when `num_peers() > 0`; keep the last tempo when Link is disabled or peers vanish (Link does this itself, `Controller.hpp:517-540`). `External` tempo policy must cover 20..999 bpm or define a ×2/÷2 lock. Link tempo is integer µs/beat (`Tempo.hpp:47-49`): 124 bpm is really 123.99991 bpm; compare beats, not micros, in session tests, and derive segment chain begins from `time_at_beat`, not summed `durationMicros` (`Fabricator.cpp:752-755`, `CraftWork.cpp:415-429`).
9. **Link transport is not XJ transport.** The Link timeline runs while stopped (`Link.hpp:43-44`); XJ "Hold", layer mutes and network-loss "keep playing" must not be expressed as Link stop. Decide start/stop sync participation explicitly; default off keeps an MPC's Stop button from silencing the room.
10. **Callbacks run on Link's thread under a mutex.** `set_*_callback` closures are `FnMut + Send + 'static`; forward into the station loop through a channel or atomics, never call back into Link's `set_*_callback` from inside one (`Link.ipp:62-76,113-133`), and do not rely on them for scheduling (the tempo callback fires only on change, `Controller.hpp:377-380`).
11. **rusty_link gaps to close in a fork:** no custom clock, no `ticksToMicros`, no session id, no Link Audio; `HostTimeFilter::reset()` allocates and two `assert!`s can panic in the callback; `delete_*_callback` exists but there is no way to receive the `void *context` safely without the crate's trampolines. Budget the fork, and remember the proprietary license must cover it (`README.md:88-92`).
12. **MIDI clock for the `session` fallback and for Link-less gear:** `F8` at 24 ppqn from `time_at_beat(k/24)`, `FA` before the first clock of a downbeat, `FC`/`F2`/`FB` for re-sync, SPP wraps after 16,384 sixteenths (about 33 min at 124 bpm), `midir` sends are untimestamped so a dedicated high-priority sender thread is required. Nothing in `engine/` or `workstation/` has MIDI today (0 files).
13. **`numPeers()` excludes self and is "in my session".** `requestBeatAtTime` silently becomes `forceBeatAtTime` when it is 0 (`Link.ipp:145,239-247`); a station that re-anchors while momentarily alone will drag any peer that joins a moment later. Gate re-anchoring on `peers() > 0` having been stable, or do it only at join.
